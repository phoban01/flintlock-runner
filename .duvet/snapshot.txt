SPECIFICATION: [GitLab protocol](docs/requirements/01-gitlab-protocol.md)
  SECTION: [Library basis](#library-basis)
    TEXT[!MUST]: - **GL-001**
    TEXT[!MUST,implementation,test]: The Runner SHALL be a single Go program that imports the
    TEXT[!MUST,implementation,test]:   gitlab-runner `common`, `network`, `shells` and `executors` packages and
    TEXT[!MUST,implementation,test]:   SHALL NOT execute a `gitlab-runner` binary.
    TEXT[!MUST]: - **GL-002** The Runner SHALL perform every request to the GitLab API through
    TEXT[!MUST]:   the `GitLabClient` type of the gitlab-runner `network` package.
    TEXT[!MUST]: - **GL-003** The Runner SHALL pin the gitlab-runner module to an explicit
    TEXT[!MUST]:   commit and record that commit in `go.mod`.
    TEXT[!MUST]: - **GL-004** The Runner SHALL drive job acquisition and execution through the
    TEXT[!MUST]:   gitlab-runner run loop (`commands.NewRunCommand`) with a provider registry
    TEXT[!MUST]:   that contains the Executor, so that graceful shutdown, token rotation and
    TEXT[!MUST]:   the session server come from the library unchanged.

  SECTION: [Authentication](#authentication)
    TEXT[!MUST]: - **GL-010** The Runner SHALL authenticate to GitLab with a runner
    TEXT[!MUST]:   authentication token (a token beginning with `glrt-`) supplied by
    TEXT[!MUST]:   configuration.
    TEXT[!MUST]: - **GL-011** The Runner SHALL NOT call the runner registration endpoint
    TEXT[!MUST]:   `POST /api/v4/runners`.
    TEXT[!MUST]: - **GL-012** When starting, the Runner SHALL load a persistent system
    TEXT[!MUST]:   identifier from its state directory or generate and store one if none
    TEXT[!MUST]:   exists.
    TEXT[!MUST]: - **GL-013** The Runner SHALL send its system identifier as `system_id` on
    TEXT[!MUST]:   every runner-scoped request to GitLab.
    TEXT[!MUST]: - **GL-014** When starting, the Runner SHALL call `POST /api/v4/runners/verify`
    TEXT[!MUST]:   with the full `info` payload before it requests any Job.
    TEXT[!MUST]: - **GL-015** If token verification returns a forbidden response, then the
    TEXT[!MUST]:   Runner SHALL log the failure and exit with a non-zero status.
    TEXT[!MUST]: - **GL-016** Where GitLab reports a token expiry time, the Runner SHALL rotate
    TEXT[!MUST]:   the token through `POST /api/v4/runners/reset_authentication_token` before
    TEXT[!MUST]:   that time is reached.

  SECTION: [Advertised capabilities](#advertised-capabilities)
    TEXT[!MUST]: - **GL-020** The Runner SHALL advertise the executor name `flintlock` in the
    TEXT[!MUST]:   `info.executor` field of every job request.
    TEXT[!MUST]: - **GL-021** The Runner SHALL advertise `bash` as its default shell.
    TEXT[!MUST]: - **GL-022** The Runner SHALL advertise the features `variables`, `image`,
    TEXT[!MUST]:   `refspecs`, `masking`, `raw_variables`, `artifacts`, `artifacts_exclude`,
    TEXT[!MUST]:   `upload_multiple_artifacts`, `upload_raw_artifacts`, `cache`,
    TEXT[!MUST]:   `fallback_cache_keys`, `multi_build_steps`, `return_exit_code`,
    TEXT[!MUST]:   `trace_reset`, `trace_checksum`, `trace_size`, `cancelable` and
    TEXT[!MUST]:   `cancel_gracefully`.
    TEXT[!MUST]: - **GL-023** The Runner SHALL NOT advertise the `services`, `session`,
    TEXT[!MUST]:   `terminal`, `proxy` or `shared` features.
    TEXT[!MUST]: - **GL-024** If a Job declares services, then the Runner SHALL fail the Job
    TEXT[!MUST]:   with the failure reason `runner_unsupported` and a log line stating that
    TEXT[!MUST]:   services are not supported by this executor.

  SECTION: [Job acquisition](#job-acquisition)
    TEXT[!MUST]: - **GL-030** The Runner SHALL request a Job from GitLab only after the
    TEXT[!MUST]:   Scheduler has granted a Reservation for it.
    TEXT[!MUST]: - **GL-031** When GitLab returns no job, the Runner SHALL send the
    TEXT[!MUST]:   `X-GitLab-Last-Update` value it received as `last_update` in the next
    TEXT[!MUST]:   request so that GitLab long-polls instead of returning immediately.
    TEXT[!MUST]: - **GL-032** When GitLab returns no job, the Runner SHALL release the
    TEXT[!MUST]:   Reservation before the next request is made.
    TEXT[!MUST]: - **GL-033** The Runner SHALL run no more Jobs concurrently than the
    TEXT[!MUST]:   configured concurrency limit.
    TEXT[!MUST]: - **GL-034** When a Job is received, the Runner SHALL report the Job as
    TEXT[!MUST]:   `running` to GitLab before any Stage executes.
    TEXT[!MUST]: - **GL-035** If the transition to `running` is rejected by GitLab, then the
    TEXT[!MUST]:   Runner SHALL abandon the Job without executing any Stage and SHALL release
    TEXT[!MUST]:   its Reservation.

  SECTION: [Job execution](#job-execution)
    TEXT[!MUST]: - **GL-040** The Runner SHALL execute the Stages of a Job in the order
    TEXT[!MUST]:   defined by the gitlab-runner `common` package.
    TEXT[!MUST]: - **GL-041** The Runner SHALL generate each Stage script with the `bash`
    TEXT[!MUST]:   shell implementation of the gitlab-runner `shells` package.
    TEXT[!MUST]: - **GL-042** The Runner SHALL enforce the Job timeout carried in the Job's
    TEXT[!MUST]:   `runner_info.timeout` field by cancelling the Job's context when it elapses.
    TEXT[!MUST]: - **GL-043** When a Job's context is cancelled because its timeout elapsed,
    TEXT[!MUST]:   the Runner SHALL report the failure reason `job_execution_timeout`.
    TEXT[!MUST]: - **GL-044** The Runner SHALL clone the repository inside the MicroVM using
    TEXT[!MUST]:   the Job token embedded by the generated `get_sources` script.
    TEXT[!MUST]: - **GL-045** The Runner SHALL upload Job artifacts to GitLab with the Job
    TEXT[!MUST]:   token from within the MicroVM using the helper invocation generated by the
    TEXT[!MUST]:   shell.
    TEXT[!MUST]: - **GL-046** The Runner SHALL download dependency artifacts with each
    TEXT[!MUST]:   dependency's own token as provided in the Job payload.

  SECTION: [Job log](#job-log)
    TEXT[!MUST]: - **GL-050** While a Job executes, the Runner SHALL stream the Job log to
    TEXT[!MUST]:   GitLab with `PATCH /api/v4/jobs/:id/trace` requests carrying a
    TEXT[!MUST]:   `Content-Range` header.
    TEXT[!MUST]: - **GL-051** The Runner SHALL honour the `X-GitLab-Trace-Update-Interval`
    TEXT[!MUST]:   header when choosing the interval between trace patches.
    TEXT[!MUST]: - **GL-052** If a trace patch returns a range-not-satisfiable response, then
    TEXT[!MUST]:   the Runner SHALL resend the log from the offset given in the response's
    TEXT[!MUST]:   `Range` header.
    TEXT[!MUST]: - **GL-053** The Runner SHALL mask the values of Job variables flagged as
    TEXT[!MUST]:   masked before they are written to the Job log.
    TEXT[!MUST]: - **GL-054** The Runner SHALL truncate the Job log at the configured output
    TEXT[!MUST]:   limit and record the truncation in the log.

  SECTION: [Cancellation and completion](#cancellation-and-completion)
    TEXT[!MUST]: - **GL-060** When GitLab returns a `Job-Status` header of `canceled` on a
    TEXT[!MUST]:   trace patch or job update, the Runner SHALL stop the current Stage, run the
    TEXT[!MUST]:   `after_script` Stage and report the Job as failed with the reason
    TEXT[!MUST]:   `job_canceled`.
    TEXT[!MUST]: - **GL-061** When GitLab returns a `Job-Status` header of `failed`, the Runner
    TEXT[!MUST]:   SHALL abort the Job immediately without running `after_script`.
    TEXT[!MUST]: - **GL-062** When a Job finishes, the Runner SHALL report the final state,
    TEXT[!MUST]:   the failure reason where applicable, the exit code of the failing Stage and
    TEXT[!MUST]:   the checksum and size of the Job log to GitLab.
    TEXT[!MUST]: - **GL-063** If the final job update returns an accepted-but-pending
    TEXT[!MUST]:   response, then the Runner SHALL retry the update with backoff until GitLab
    TEXT[!MUST]:   confirms it or the configured retry limit is reached.
    TEXT[!MUST]: - **GL-064** If a failure reason is not in the list GitLab advertised as
    TEXT[!MUST]:   supported, then the Runner SHALL report `runner_system_failure` in its
    TEXT[!MUST]:   place.

  SECTION: [Shutdown](#shutdown)
    TEXT[!MUST]: - **GL-070** When the Runner receives `SIGTERM` or `SIGQUIT`, the Runner SHALL
    TEXT[!MUST]:   stop requesting Jobs and release every unconverted Reservation.
    TEXT[!MUST]: - **GL-071** While a graceful shutdown is in progress, the Runner SHALL allow
    TEXT[!MUST]:   running Jobs to finish for up to the configured shutdown timeout.
    TEXT[!MUST]: - **GL-072** If running Jobs have not finished when the shutdown timeout
    TEXT[!MUST]:   elapses, then the Runner SHALL cancel them, report them as failed with the
    TEXT[!MUST]:   reason `runner_system_failure` and release their MicroVMs.
    TEXT[!MUST]: - **GL-073** When the Runner receives a second termination signal during a
    TEXT[!MUST]:   graceful shutdown, the Runner SHALL cancel all running Jobs immediately.

SPECIFICATION: [Executor](docs/requirements/02-executor.md)
  SECTION: [Interface](#interface)
    TEXT[!MUST]: - **EX-001** The Executor SHALL implement the `ExecutorProvider` and
    TEXT[!MUST]:   `Executor` interfaces of the gitlab-runner `common` package.
    TEXT[!MUST]: - **EX-002** The Executor SHALL be registered in the provider registry under
    TEXT[!MUST]:   the executor name `flintlock`.
    TEXT[!MUST]: - **EX-003** When the run loop calls `Acquire`, the Executor SHALL request a
    TEXT[!MUST]:   Reservation from the Scheduler and return it as the executor data.
    TEXT[!MUST]: - **EX-004** If the Scheduler refuses a Reservation, then the Executor SHALL
    TEXT[!MUST]:   return an error that the run loop treats as no free executor, so that no
    TEXT[!MUST]:   Job is requested from GitLab.
    TEXT[!MUST]: - **EX-005** When the run loop calls `Release`, the Executor SHALL release the
    TEXT[!MUST]:   Reservation held in the executor data.
    TEXT[!MUST]: - **EX-006** The Executor SHALL report the shell name `bash` and the feature
    TEXT[!MUST]:   set listed in the GitLab protocol document from `GetFeatures` and
    TEXT[!MUST]:   `GetDefaultShell`.

  SECTION: [Prepare](#prepare)
    TEXT[!MUST]: - **EX-010** When `Prepare` is called, the Executor SHALL ask the Scheduler to
    TEXT[!MUST]:   resolve a Profile for the Job.
    TEXT[!MUST]: - **EX-011** If no Profile can be resolved for the Job, then the Executor
    TEXT[!MUST]:   SHALL fail the Job with the failure reason `runner_unsupported` and a log
    TEXT[!MUST]:   line naming the requested Job Image.
    TEXT[!MUST]: - **EX-012** When a Profile has been resolved, the Executor SHALL ask the
    TEXT[!MUST]:   Scheduler to allocate a MicroVM for the Job and the Profile, passing the
    TEXT[!MUST]:   Job's context so that cancellation aborts the allocation.
    TEXT[!MUST]: - **EX-013** If allocation fails, then the Executor SHALL fail the Job with
    TEXT[!MUST]:   the failure reason `runner_system_failure` and a log line stating the
    TEXT[!MUST]:   allocation error.
    TEXT[!MUST]: - **EX-014** When a MicroVM has been allocated, the Executor SHALL wait until
    TEXT[!MUST]:   the Guest Transport reports the guest ready or the Profile's ready timeout
    TEXT[!MUST]:   elapses.
    TEXT[!MUST]: - **EX-015** If the guest is not ready when the ready timeout elapses, then
    TEXT[!MUST]:   the Executor SHALL release the MicroVM to the Scheduler and fail the Job
    TEXT[!MUST]:   with the failure reason `runner_system_failure`.
    TEXT[!MUST]: - **EX-016** When the guest is ready, the Executor SHALL create the Profile's
    TEXT[!MUST]:   builds directory and cache directory in the guest if they do not exist.
    TEXT[!MUST]: - **EX-017** The Executor SHALL complete `Prepare` within the configured
    TEXT[!MUST]:   prepare timeout or fail the Job.
    TEXT[!MUST]: - **EX-018** The Executor SHALL set the shell script configuration so that
    TEXT[!MUST]:   the builds directory, cache directory and helper binary path used in
    TEXT[!MUST]:   generated scripts are those of the Profile.
    TEXT[!MUST]: - **EX-019** The Executor SHALL write a collapsible section to the Job log
    TEXT[!MUST]:   during `Prepare` that names the Profile, the Pool, the Host name, the
    TEXT[!MUST]:   MicroVM uid and the time taken to become ready.

  SECTION: [Run](#run)
    TEXT[!MUST]: - **EX-020** When `Run` is called for a Stage, the Executor SHALL execute the
    TEXT[!MUST]:   Profile's shell inside the MicroVM through the Guest Transport with the
    TEXT[!MUST]:   Stage script supplied on standard input.
    TEXT[!MUST]: - **EX-021** The Executor SHALL stream the standard output and standard
    TEXT[!MUST]:   error of a Stage to the Job log as they are produced rather than after the
    TEXT[!MUST]:   Stage completes.
    TEXT[!MUST]: - **EX-022** When a Stage's command exits with a non-zero status, the
    TEXT[!MUST]:   Executor SHALL return a build error carrying that exit code so that the
    TEXT[!MUST]:   Runner reports it to GitLab.
    TEXT[!MUST]: - **EX-023** If the Guest Transport stream fails before the Stage's exit
    TEXT[!MUST]:   status is known, then the Executor SHALL return a system error and SHALL
    TEXT[!MUST]:   NOT re-run the Stage.
    TEXT[!MUST]: - **EX-024** When the Job's context is cancelled while a Stage is running,
    TEXT[!MUST]:   the Executor SHALL terminate the Stage's process in the guest and return
    TEXT[!MUST]:   within the configured graceful kill timeout.
    TEXT[!MUST]: - **EX-025** The Executor SHALL run each Stage with the working directory set
    TEXT[!MUST]:   to the Profile's builds directory.
    TEXT[!MUST]: - **EX-026** The Executor SHALL run each Stage as the user named by the
    TEXT[!MUST]:   Profile, defaulting to `root`.
    TEXT[!MUST]: - **EX-027** The Executor SHALL deliver every Job-specific value to the guest
    TEXT[!MUST]:   through the Stage scripts sent over the Guest Transport and SHALL NOT place
    TEXT[!MUST]:   Job-specific values in MicroVM metadata.

  SECTION: [Finish and cleanup](#finish-and-cleanup)
    TEXT[!MUST]: - **EX-030** When `Cleanup` is called, the Executor SHALL release the Job's
    TEXT[!MUST]:   MicroVM to the Scheduler regardless of whether the Job succeeded, failed or
    TEXT[!MUST]:   was cancelled.
    TEXT[!MUST]: - **EX-031** The Executor SHALL NOT run a second Job in a MicroVM that has
    TEXT[!MUST]:   run a Job.
    TEXT[!MUST]: - **EX-032** If `Prepare` fails after a MicroVM was allocated, then the
    TEXT[!MUST]:   Executor SHALL release that MicroVM to the Scheduler before returning.
    TEXT[!MUST]: - **EX-033** Where the keep-on-failure debug option is enabled, the Executor
    TEXT[!MUST]:   SHALL ask the Scheduler to retain the MicroVM of a failed Job instead of
    TEXT[!MUST]:   releasing it and SHALL write the MicroVM uid and Host name to the Job log.

  SECTION: [Guest Transport](#guest-transport)
    TEXT[!MUST]: - **EX-040**
    TEXT[!MUST,implementation,test]: The Guest Transport SHALL provide an operation that runs a
    TEXT[!MUST,implementation,test]:   command in a MicroVM with a working directory, environment, user, standard
    TEXT[!MUST,implementation,test]:   input stream, standard output stream, standard error stream and returns the
    TEXT[!MUST,implementation,test]:   command's exit status.
    TEXT[!MUST]: - **EX-041**
    TEXT[!MUST,implementation,test]: The Guest Transport SHALL provide a readiness operation that
    TEXT[!MUST,implementation,test]:   succeeds only when a trivial command can be executed in the guest.
    TEXT[!MUST]: - **EX-042**
    TEXT[!MUST,implementation,test]: The Guest Transport SHALL be selectable per Profile from the
    TEXT[!MUST,implementation,test]:   implementations `exec` and `ssh`, with `exec` as the default.
    TEXT[!MUST]: - **EX-043**
    TEXT[!MUST,implementation,test]: The `exec` Guest Transport SHALL use the flintlock
    TEXT[!MUST,implementation,test]:   `MicroVMExec.ExecCommand` streaming RPC of the Host that runs the MicroVM.
    TEXT[!MUST]: - **EX-044**
    TEXT[!MUST,implementation,test]: The `exec` Guest Transport SHALL send an `ExecStart` message
    TEXT[!MUST,implementation,test]:   with `has_stdin` set, followed by the Stage script as `stdin` chunks,
    TEXT[!MUST,implementation,test]:   followed by `stdin_eof`.
    TEXT[!MUST]: - **EX-045**
    TEXT[!MUST,implementation,test]: The `exec` Guest Transport SHALL treat an `exit_code`
    TEXT[!MUST,implementation,test]:   payload as the command's exit status and SHALL treat an `error` payload
    TEXT[!MUST,implementation,test]:   as a transport failure only where the stream ends without an `exit_code`.
    TEXT[!MUST]: - **EX-046**
    TEXT[!MUST,implementation,test]: The `exec` Guest Transport SHALL set the `timeout_seconds` field
    TEXT[!MUST,implementation,test]:   of `ExecStart` from the remaining time on the operation's context.
    TEXT[!MUST]: - **EX-047**
    TEXT[!MUST,implementation,test]: The `ssh` Guest Transport SHALL connect to the guest's SSH
    TEXT[!MUST,implementation,test]:   service through the flintlock `MicroVMSSHProxy.SSHProxy` streaming RPC of
    TEXT[!MUST,implementation,test]:   the Host that runs the MicroVM.
    TEXT[!MUST]: - **EX-048**
    TEXT[!MUST,implementation,test]: The `ssh` Guest Transport SHALL NOT offer a direct TCP mode,
    TEXT[!MUST,implementation,test]:   because pool MicroVMs are created from one shared template and flintlock
    TEXT[!MUST,implementation,test]:   reports no guest address the Runner could connect to.
    TEXT[!MUST]: - **EX-049**
    TEXT[!MUST,implementation,test]: The `ssh` Guest Transport SHALL authenticate with the private
    TEXT[!MUST,implementation,test]:   key named by the Profile and SHALL verify the guest host key only where the
    TEXT[!MUST,implementation,test]:   Profile provides a known host key.
    TEXT[!MUST]: - **EX-050**
    TEXT[!MUST,implementation,test]: The Guest Transport SHALL reuse the Host client's gRPC
    TEXT[!MUST,implementation,test]:   connection rather than opening a new connection per Stage.
    TEXT[!MUST]: - **EX-051**
    TEXT[!MUST,implementation,test]: If the Host that runs the MicroVM becomes unreachable, then the
    TEXT[!MUST,implementation,test]:   Guest Transport SHALL fail the in-flight operation within the configured
    TEXT[!MUST,implementation,test]:   transport deadline.
    TEXT[!MUST]: - **EX-052** A Profile's root filesystem image SHALL carry a guest agent
    TEXT[!MUST]:   that emits liveness heartbeats on the exec control channel, because
    TEXT[!MUST]:   `flintlockd` ends an exec session whose control channel has been idle
    TEXT[!MUST]:   for longer than its deadline.

  SECTION: [Host service environment](#host-service-environment)
    TEXT[!MUST]: - **EX-060** When the Placement of a Job's MicroVM is known, the Executor
    TEXT[!MUST]:   SHALL add to the Job's environment the variables that point at the Host
    TEXT[!MUST]:   Services of that Host: `BUILDKIT_HOST`, `GOPROXY`, `GOFLAGS` with
    TEXT[!MUST]:   `-modcacherw`, the registry mirror address as `CI_REGISTRY_MIRROR`, and
    TEXT[!MUST]:   one variable per configured HTTP cache upstream under the name given in
    TEXT[!MUST]:   the configuration.
    TEXT[!MUST]: - **EX-065** When the Go module proxy is configured with private module
    TEXT[!MUST]:   patterns, the Executor SHALL set `GONOSUMDB` to those patterns and
    TEXT[!MUST]:   `GONOPROXY` to the empty string so that the Go toolchain fetches private
    TEXT[!MUST]:   modules through the Host's proxy and does not consult the public checksum
    TEXT[!MUST]:   database for them.
    TEXT[!MUST]: - **EX-066** The Executor SHALL NOT set `GOPRIVATE`, because it would make
    TEXT[!MUST]:   the Go toolchain bypass the Host's proxy for private modules.
    TEXT[!MUST]: - **EX-061** The Executor SHALL NOT override a variable that the Job itself
    TEXT[!MUST]:   sets with the same name, so that a job can opt out of a Host Service.
    TEXT[!MUST]: - **EX-062** Where a Host Service is disabled or the Host's Inventory entry
    TEXT[!MUST]:   lacks its address, the Executor SHALL omit that service's variables rather
    TEXT[!MUST]:   than point them at an unreachable address.
    TEXT[!MUST]: - **EX-063** The Executor SHALL add the Host Service variables before the
    TEXT[!MUST]:   `prepare_script` Stage so that every Stage, including `get_sources`, sees
    TEXT[!MUST]:   them.
    TEXT[!MUST]: - **EX-064** The Executor SHALL write a line to the `flintlock_prepare`
    TEXT[!MUST]:   section of the Job log naming the Host Services that were made available
    TEXT[!MUST]:   to the Job.

SPECIFICATION: [Scheduler](docs/requirements/03-scheduler.md)
  SECTION: [Capacity](#capacity)
    TEXT[!MUST]: - **SC-001** The Scheduler SHALL maintain a count of held Reservations and
    TEXT[!MUST]:   active Allocations and SHALL treat their sum as the number of Slots in use.
    TEXT[!MUST]: - **SC-002** The Scheduler SHALL compute available capacity as the lesser of
    TEXT[!MUST]:   the number of unused Slots and the sum of the number of available warm
    TEXT[!MUST]:   MicroVMs across all Pools.
    TEXT[!MUST]: - **SC-003** When a Reservation is requested and available capacity is
    TEXT[!MUST]:   greater than zero, the Scheduler SHALL grant a Reservation and count it as
    TEXT[!MUST]:   a Slot in use.
    TEXT[!MUST]: - **SC-004** When a Reservation is requested and available capacity is zero,
    TEXT[!MUST]:   the Scheduler SHALL refuse the Reservation.
    TEXT[!MUST]: - **SC-005** When a Reservation is released without an Allocation, the
    TEXT[!MUST]:   Scheduler SHALL return its Slot immediately.
    TEXT[!MUST]: - **SC-006** Where a Profile has a configured maximum concurrency, the
    TEXT[!MUST]:   Scheduler SHALL NOT hold more Allocations for that Profile than the
    TEXT[!MUST]:   maximum.
    TEXT[!MUST]: - **SC-007** The Scheduler SHALL be safe for concurrent use by the number of
    TEXT[!MUST]:   workers the run loop starts.
    TEXT[!MUST]: - **SC-008** When starting, the Scheduler SHALL NOT grant any Reservation
    TEXT[!MUST]:   until it has successfully contacted the Pool Manager at least once.
    TEXT[!MUST]: - **SC-009** The Scheduler SHALL count a Pool's MicroVMs that are being
    TEXT[!MUST]:   provisioned or running create hooks as unavailable when computing
    TEXT[!MUST]:   capacity.

  SECTION: [Profile resolution](#profile-resolution)
    TEXT[!MUST]: - **SC-010** The Scheduler SHALL resolve a Profile for a Job by matching the
    TEXT[!MUST]:   Job Image name against Profile image names exactly, then against Profile
    TEXT[!MUST]:   image glob patterns in configuration order, then by falling back to the
    TEXT[!MUST]:   Default Profile.
    TEXT[!MUST]: - **SC-011** If a Job has no Job Image and no Default Profile is configured,
    TEXT[!MUST]:   then the Scheduler SHALL report that no Profile can be resolved.
    TEXT[!MUST]: - **SC-012** If a Job Image matches no Profile and the configuration does not
    TEXT[!MUST]:   allow falling back to the Default Profile for unknown images, then the
    TEXT[!MUST]:   Scheduler SHALL report that no Profile can be resolved.
    TEXT[!MUST]: - **SC-013** The Scheduler SHALL resolve the Profile before claiming any
    TEXT[!MUST]:   MicroVM so that a Job with an unknown image fails without consuming a warm
    TEXT[!MUST]:   MicroVM.

  SECTION: [Allocation](#allocation)
    TEXT[!MUST]: - **SC-020** When an Allocation is requested for a Profile, the Scheduler
    TEXT[!MUST]:   SHALL claim a warm MicroVM from the Profile's Pool.
    TEXT[!MUST]: - **SC-021** If the Pool has no warm MicroVM available, then the Scheduler
    TEXT[!MUST]:   SHALL retry the claim with exponential backoff, waking early on a Pool
    TEXT[!MUST]:   Manager event that reports a MicroVM in that Pool becoming available,
    TEXT[!MUST]:   until the allocation timeout elapses.
    TEXT[!MUST]: - **SC-022** If the allocation timeout elapses before a MicroVM is claimed,
    TEXT[!MUST]:   then the Scheduler SHALL return an allocation error naming the Profile and
    TEXT[!MUST]:   the Pool.
    TEXT[!MUST]: - **SC-023** When the Job's context is cancelled during allocation, the
    TEXT[!MUST]:   Scheduler SHALL stop the allocation and release any Lease that was
    TEXT[!MUST]:   obtained.
    TEXT[!MUST]: - **SC-024** The Scheduler SHALL record for every Allocation the Job id, the
    TEXT[!MUST]:   Profile name, the MicroVM uid, the Lease id and the Placement.
    TEXT[!MUST]: - **SC-025** The Scheduler SHALL log every allocation with the Job id,
    TEXT[!MUST]:   Profile, Host name, MicroVM uid and elapsed time from claim to Placement.
    TEXT[!MUST]: - **SC-026** The Scheduler SHALL convert a Reservation into an Allocation
    TEXT[!MUST]:   without releasing the Slot in between.

  SECTION: [Placement](#placement)
    TEXT[!MUST]: - **SC-030** When a claim succeeds and the response carries a `host` with a
    TEXT[!MUST]:   name, the Scheduler SHALL record that name as the Placement, and if the
    TEXT[!MUST]:   `host.address` differs from the Inventory entry of that name, then the
    TEXT[!MUST]:   Scheduler SHALL log a warning with both values, count the mismatch and
    TEXT[!MUST]:   continue using the Inventory endpoint.
    TEXT[!MUST]: - **SC-031** When a claim succeeds and the response does not name the Host,
    TEXT[!MUST]:   the Scheduler SHALL resolve the Placement by calling `GetMicroVM` with the
    TEXT[!MUST]:   MicroVM's uid on each Host the Pool Manager reports for that Pool until
    TEXT[!MUST]:   one returns it.
    TEXT[!MUST]: - **SC-032** The Scheduler SHALL cache the Placement of a MicroVM for the
    TEXT[!MUST]:   lifetime of its Lease.
    TEXT[!MUST]: - **SC-033** If Placement cannot be resolved for a MicroVM, then the
    TEXT[!MUST]:   Scheduler SHALL release its Lease and report an allocation error.
    TEXT[!MUST]: - **SC-034** If the Host named in a Placement is not in the Inventory, then
    TEXT[!MUST]:   the Scheduler SHALL release the Lease and report an allocation error
    TEXT[!MUST]:   naming the Host.

  SECTION: [Host health](#host-health)
    TEXT[!MUST]: - **SC-040** The Scheduler SHALL probe every Host in the Inventory at the
    TEXT[!MUST]:   configured health interval by calling `ServerInfo`, falling back to
    TEXT[!MUST]:   `ListMicroVMs` on the Runner's namespace when `ServerInfo` is not
    TEXT[!MUST]:   implemented by the Host.
    TEXT[!MUST]: - **SC-041** When a Host fails the configured number of consecutive probes,
    TEXT[!MUST]:   the Scheduler SHALL mark the Host unhealthy.
    TEXT[!MUST]: - **SC-042** When an unhealthy Host passes a probe, the Scheduler SHALL mark
    TEXT[!MUST]:   the Host healthy.
    TEXT[!MUST]: - **SC-043** When a Host becomes unhealthy, the Scheduler SHALL abort every
    TEXT[!MUST]:   Job whose MicroVM is placed on that Host with the failure reason

    TEXT[!MUST]: - **SC-044** The Scheduler SHALL NOT refuse Reservations because a Host is

    TEXT[!MUST]:   the Pool Manager and SHALL NOT delete the MicroVM itself.

    TEXT[!MUST]:   exponential backoff up to the configured retry limit and SHALL then log

    TEXT[!MUST]: - **SC-053** When starting, the Scheduler SHALL NOT attempt to find or clean

    TEXT[!MUST]:   heartbeats expire and the Pool Manager deletes them.
    TEXT[!MUST]: - **SC-054** Where the keep-on-failure debug option is enabled, the Scheduler
    TEXT[!MUST]:   SHALL keep heartbeating the Lease of a failed Job for the configured keep
    TEXT[!MUST]:   duration before releasing it, and SHALL log the MicroVM uid and Host name.

  SECTION: [Lease keep-alive](#lease-keep-alive)
    TEXT[!MUST]: - **SC-060** While an Allocation holds a Lease, the Scheduler SHALL send a
    TEXT[!MUST]:   heartbeat to the Pool Manager at an interval no longer than half the time
    TEXT[!MUST]:   remaining until the Lease expiry it last received.
    TEXT[!MUST]: - **SC-061** If a heartbeat reports that the Lease no longer exists, then the
    TEXT[!MUST]:   Scheduler SHALL abort the Job with the failure reason
    TEXT[!MUST]:   `runner_system_failure` and drop the Allocation without a release call.
    TEXT[!MUST]: - **SC-062** If heartbeats fail for longer than the Lease expiry, then the
    TEXT[!MUST]:   Scheduler SHALL treat the Lease as lost and abort the Job.
